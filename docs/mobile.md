# Overlock 모바일 대응 계획

- 대상 엔진: Godot 4.6.1 (GL Compatibility), 웹 export(스레드 OFF 빌드)
- 범위: 모바일 브라우저에서 웹 빌드를 끝까지 플레이할 수 있게 만드는 작업입니다. 시뮬레이션 코드(`scripts/player/`, `RunStats`, `InputFrame`, `PlayerController`, `TrackData`)는 이 계획의 어느 단계에서도 수정하지 않습니다.
- 관련 문서: 시뮬레이션 구조는 `architecture.md`, 표현 계층은 `presentation.md`, 배포는 `deploy.md`에 정리되어 있습니다.

---

## 1. 목표 플랫폼

현재 유력한 배포 경로는 웹 export입니다(https://overlock.bnbong.com, itch.io 배포 준비 중). 네이티브 Android/iOS 앱은 계획에 없습니다. 따라서 이 문서에서 말하는 "모바일 대응"은 다음 두 브라우저에서 웹 빌드를 가로 화면으로 플레이할 수 있는 상태를 뜻합니다.

| 플랫폼 | 브라우저 | 비고 |
|---|---|---|
| iOS / iPadOS | Safari (그리고 같은 WebKit을 쓰는 iOS용 Chrome) | 최우선 검증 대상입니다. 오디오와 전체 화면 제약이 가장 많습니다. |
| Android | Chrome | 두 번째 검증 대상입니다. |

네이티브 export로 가는 길은 §5.6에 짧게 정리했습니다.

## 2. 현황 진단

### 2.1 입력

- `InputSetup.gd`가 InputMap 액션 8종(`steer_left`, `steer_right`, `speed_up`, `speed_down`, `drift`, `restart`, `pause`, `to_menu`)을 키보드 물리 키코드로 등록합니다. 1단계 이전에는 터치로 이 액션을 누를 방법이 없었습니다.
- `RaceDirector.gd`는 조향과 드리프트를 `Input.is_action_pressed`로 매 물리 틱에 읽고, 속도 단계와 일시정지, 재시작은 `_unhandled_input`에서 `is_action_pressed` 이벤트로 버퍼링합니다. 이 값은 60Hz 고정 스텝에서 `InputFrame`으로 묶여 `PlayerController`에 전달됩니다.
- 조향 입력은 디지털입니다. `_sample_input()`은 좌/우 액션이 눌렸는지만 보고 `steer`에 -1, 0, +1 중 하나를 넣습니다. 이 구조 덕분에 터치 버튼이 키보드와 완전히 같은 값을 만들 수 있습니다(§3).
- 메뉴 계열 화면은 전부 `Button`, `HSlider`, `LineEdit` 같은 표준 GUI 노드로 구성되어 있습니다. `input_devices/pointing/emulate_mouse_from_touch`가 기본값(true)이므로 첫 번째 손가락의 터치가 마우스 왼쪽 클릭으로 변환되어 이 노드들을 누릅니다.

### 2.2 화면 비율

- 기준 해상도는 1280×720이고, stretch mode는 `canvas_items`입니다. `aspect`는 지정하지 않았지만 Godot 4.6.1의 기본값이 이미 `keep`이므로, 1단계 이전에도 16:9가 아닌 화면에서는 비율을 유지한 채 레터박스가 적용되고 있었습니다.
- 요즘 스마트폰 가로 화면은 대부분 16:9보다 가로가 깁니다. 예를 들어 844×390(CSS px) 화면은 약 19.5:9입니다.
- 웹 export 프리셋은 `html/canvas_resize_policy=2`(Adaptive)라서 캔버스가 브라우저 창 전체를 채웁니다. 기본 HTML 셸에는 이미 `width=device-width, user-scalable=no, initial-scale=1.0` 뷰포트 메타와 `touch-action: none` 스타일이 들어 있습니다.

### 2.3 성능

- 렌더러는 GL Compatibility이고, 웹에서는 WebGL 2로 동작합니다. `rendering_method.mobile`도 `gl_compatibility`로 지정되어 있습니다.
- 매 프레임 비용이 큰 요소는 원단 원근 셰이더(`fabric_mode7.gdshader`)와 그 입력인 `FabricSource` SubViewport(512×512, 항상 갱신, 2D MSAA 2x)입니다. 전체 화면 셰이더가 픽셀마다 한 번씩 돌기 때문에, 고해상도 폰에서는 GPU 부하가 데스크톱보다 상대적으로 커질 수 있습니다.
- 현재 웹 빌드 크기는 `index.wasm` 37,685,705바이트, `index.pck` 7,728,084바이트입니다(8월 빌드 기준 수치이며, 최근 스크래치 빌드의 `index.pck`는 25,999,696바이트로 더 큽니다). 모바일 데이터 환경에서는 첫 로딩 시간이 길어질 수 있습니다.
- 시뮬레이션은 60Hz 고정 스텝이므로 프레임이 떨어져도 판정 결과는 바뀌지 않습니다. 다만 렌더 프레임이 크게 떨어지면 입력 반응이 둔하게 느껴질 수 있습니다.

### 2.4 오디오

- 웹 오디오 재생 타입 문제는 `AudioManager`가 웹에서 `PLAYBACK_TYPE_STREAM`을 강제하는 방식으로 이미 해결되어 있습니다.
- 모바일 브라우저는 사용자 제스처가 발생하기 전에는 AudioContext를 `suspended` 상태로 둡니다. Godot 4.6.1 소스(`platform/web/display_server_web.cpp`의 `_touch_callback`)를 확인한 결과, 엔진이 `touchstart`와 `touchend` 이벤트마다 `OS_Web::resume_audio()`를 호출하고, 이 함수는 JS 쪽 `godot_audio_resume()`을 통해 `AudioContext.resume()`을 실행합니다. 키 입력과 마우스 버튼 콜백에서도 같은 호출을 합니다.
- HTML 사양에서 사용자 활성화로 인정되는 이벤트는 `touchend`입니다(`touchstart`는 인정되지 않습니다). 엔진이 `touchend`에서도 resume을 호출하므로, 첫 탭을 뗄 때 오디오가 풀리는 것이 정상 동작입니다. 따라서 게임 코드에서 별도로 AudioContext를 풀어 줄 필요는 없다고 판단했습니다. 이 판단은 실기에서 확인해야 합니다(§6.2).
- 메뉴 BGM은 `MainMenu._ready`에서 재생을 시작합니다. 첫 탭 전까지는 AudioContext가 멈춰 있으므로 BGM도 들리지 않다가, 첫 탭(닉네임 확인이나 Start) 이후에 이어서 재생될 것으로 예상합니다.

## 3. 공정성 원칙

리더보드는 모든 플랫폼의 기록을 한 표에서 비교합니다. 그래서 모바일 입력은 다음 원칙을 지켜야 합니다.

1. **터치 입력은 키보드 입력과 등가여야 합니다.** 터치 버튼은 키를 흉내 내지 않고 같은 InputMap 액션을 직접 누르고 뗍니다. 조향은 원래 디지털 입력이라서, 터치로 누르든 키보드로 누르든 `InputFrame.steer`에는 똑같이 -1, 0, +1만 들어갑니다. 좌우를 동시에 누르면 0이 되는 규칙도 같습니다. 속도 버튼 한 번 탭은 키 한 번 누름과 같은 한 단계 변화입니다. 따라서 시뮬레이션 관점에서 두 입력 장치는 구별되지 않고, 결정론과 기록 비교 기준도 그대로 유지됩니다.
2. **아날로그 조향(가상 조이스틱, 기울기 센서, 누르는 세기)은 도입하지 않습니다.** 조향 동역학(조향 곡선, 반전 부스트, 드리프트 각속도 배율)은 모두 "눌림/안 눌림" 입력을 전제로 튜닝되어 있습니다. 0과 1 사이의 조향값을 허용하면 키보드로는 낼 수 없는 궤적이 가능해지고, 한쪽 입력 장치가 유리해집니다. 아날로그 값을 받으려면 시뮬레이션 코드를 고쳐야 하므로, 기존 기록과의 비교도 깨집니다. 이 프로젝트는 이미 조향 감도 설정에서 풀락 반경이 바뀌는 방식(turn_power 배율)을 불공정하다고 판정해 도입하지 않은 전례가 있습니다.
3. **입력 타이밍 차이를 만들지 않습니다.** 터치에서 주입한 액션 이벤트와 키보드 이벤트는 모두 `Input`의 버퍼를 거쳐 다음 프레임 시작에 처리됩니다. 추가 지연이나 선입력 이점은 생기지 않습니다.
4. **자동 보조 기능(자동 조향, 자동 속도)은 넣지 않습니다.** 조작 편의가 필요하면 버튼 배치와 크기로 해결합니다.

## 4. 1단계: 터치 컨트롤과 화면 비율 (이번 구현)

### 4.1 터치 컨트롤 구조

새 파일 `game/scripts/ui/TouchControls.gd`(Control)가 온스크린 버튼 6개를 그립니다. `HUD.gd`가 `_ready`에서 이 노드를 동적으로 생성하므로 `Gameplay.tscn`은 수정하지 않았습니다.

- 좌측 하단: ◀ ▶ 조향 버튼(각 112×112)
- 우측 하단: ▲ ▼ 속도 버튼(각 112×112)과 DRIFT 홀드 버튼(132×132)
- 우측 상단: ‖ 일시정지 버튼(80×80, TIME 패널 왼쪽)

버튼을 누르거나 떼면 `InputEventAction`(액션 이름, pressed)을 만들어 `Input.parse_input_event()`로 보냅니다. 이렇게 하면 `Input.is_action_pressed`(조향, 드리프트)와 `_unhandled_input`(속도, 일시정지)이 키보드와 같은 경로로 값을 받습니다. `RaceDirector.gd`는 수정하지 않았습니다.

**멀티터치 처리 방식으로 `InputEventScreenTouch` 인덱스 직접 추적을 선택했습니다.** 검토한 두 방식을 비교하면 다음과 같습니다.

| 기준 | TouchScreenButton | 인덱스 직접 추적(선택) |
|---|---|---|
| 멀티터치, 미끄러져 들어오기(passby) | 기본 지원합니다. | `ScreenTouch`와 `ScreenDrag`의 index별로 현재 버튼을 기록해 직접 구현합니다(약 60줄). |
| 레이아웃 | Node2D라서 앵커를 쓸 수 없습니다. HUD의 다른 위젯은 Control 앵커로 배치되어 있어 좌표계를 따로 맞춰야 합니다. | Control이므로 뷰포트 크기에 맞춰 사각형을 계산하고, HUD 위젯과 같은 좌표계에서 겹침을 검사할 수 있습니다. |
| 버튼별 규칙 | 모든 버튼에 같은 passby 규칙이 적용됩니다. | 조향·드리프트는 미끄러져 들어오기를 허용하고, 속도·일시정지는 터치가 시작된 버튼에서만 눌림을 인정하도록 버튼마다 다르게 정할 수 있습니다. 속도 버튼에 passby를 허용하면 손가락이 지나가기만 해도 속도 단계가 바뀌는 오조작이 생깁니다. |
| 데스크톱 검증 | 실제 터치 이벤트만 받습니다. | `--touch-controls` 강제 모드에서 실제 마우스 왼쪽 버튼도 터치 한 개처럼 받게 만들 수 있습니다. |
| 판정 영역 | 텍스처나 Shape2D로 지정합니다. | 시각 사각형보다 8px 넓은 판정 영역을 코드로 둘 수 있습니다. |

추가로 지켜야 할 세부 동작은 다음과 같습니다.

- 같은 버튼을 손가락 두 개가 누르면 첫 누름에서만 pressed를 보내고, 마지막 손가락이 떨어질 때 released를 보냅니다.
- 버튼이 숨겨질 때(일시정지, 모달, 완주 줌아웃)와 창이나 앱 포커스를 잃을 때는 눌린 액션을 모두 뗍니다. 손가락을 뗀 이벤트가 그 이후에 오거나 아예 오지 않더라도 액션이 눌린 채 남지 않습니다.
- 버튼 위에서 시작한 터치는 `set_input_as_handled()`로 처리 완료 표시를 합니다. 버튼 밖의 터치는 그대로 통과합니다.
- 루트 Control은 `mouse_filter=IGNORE`이고 입력은 `_input`에서 직접 받습니다. `process_mode`는 `ALWAYS`입니다(HUD는 PAUSABLE이므로 일시정지 중에도 뗌 처리를 하려면 필요합니다).

### 4.2 레이아웃

버튼 위치는 HUD 위젯을 피하도록 정했습니다(모두 1280×720 기준 좌표입니다).

| 버튼 | 사각형 | 피한 위젯 |
|---|---|---|
| ◀ | (152, 580) 112×112 | RISK 패널(16~136, 534~684), 그 위 효과 카드 스택 |
| ▶ | (280, 580) 112×112 | 같음 |
| ▲ | (998, 440) 112×112 | SPEED 패널(1130~1272, 442~680) |
| ▼ | (998, 568) 112×112 | 같음 |
| DRIFT | (850, 548) 132×132 | 같음 |
| ‖ | (946, 10) 80×80 | TIME 패널(1042~1272, 6~92) |

색은 `SewingSkin` 팔레트를 씁니다. 평소에는 반투명 베이지(FABRIC, 알파 0.34)에 보라 박음질 테두리를 그리고, 누르면 보라(THREAD_PURPLE, 알파 0.72)로 채우고 글리프를 크림색으로 바꿉니다.

터치 모드에서는 키 이름 힌트를 정리합니다. 하단 중앙의 "←/→ TURN ⇧ DRIFT" 힌트를 숨기고, 속도 게이지 캡션은 "FASTER"/"SLOWER"로 바꿉니다.

### 4.3 표시 조건

`TouchControls.should_show()`가 다음 중 하나를 만족하면 버튼을 생성합니다.

1. 커맨드라인 사용자 인자에 `--touch-controls`가 있습니다(데스크톱 검증용).
2. `DisplayServer.is_touchscreen_available()`이 true입니다. 웹에서는 JS `"ontouchstart" in window`로 판별합니다.
3. 웹에서 `navigator.maxTouchPoints > 0`입니다(`JavaScriptBridge`, 웹 한정 보조 판별).

튜토리얼 모달(`TutorialDialog`)은 2번 기준만 씁니다. 두 기준이 어긋나는 경우는 3번만 참인 환경(예: 터치 이벤트가 꺼진 데스크톱 Firefox와 터치 노트북 조합)뿐입니다. 이때는 버튼은 보이는데 튜토리얼은 키보드 안내를 보여 줍니다. 필요하면 튜토리얼도 `TouchControls.should_show()`를 쓰도록 통일합니다.

터치 노트북처럼 키보드와 터치스크린이 함께 있는 기기에서도 버튼이 보입니다. 버튼은 반투명이고 키보드 입력과 충돌하지 않으므로 그대로 둡니다.

### 4.4 일시정지, 완주 스킵, 모달

- **일시정지 오버레이**: 터치 모드에서만 키보드 힌트("[Esc] Resume ...")를 숨기고 "계속", "재시작", "메인" 버튼 3개를 추가합니다. 각 버튼은 `pause`, `restart`, `to_menu` 액션의 눌림과 뗌을 연속으로 주입하므로 Esc, R, M 키와 같은 결과를 냅니다. 버튼 행은 `PROCESS_MODE_ALWAYS`라서 트리가 일시정지된 상태에서도 눌립니다. 시트 스킨 버튼(UiSkin small/large)은 세로로 늘리면 모서리 단추 장식이 반복되어 깨지기 때문에, 실측 136×80(높이 80px)의 재봉 팔레트 StyleBoxFlat을 따로 적용했습니다.
- **완주 줌아웃 스킵**: §2.6에 적은 원인 때문에, 터치 모드에서는 `HUD._input`이 GUI보다 먼저 터치 눌림을 보고 임의 액션(`drift`)의 눌림과 뗌을 주입합니다. `RaceDirector`는 FINISH_VIEW 상태에서 "눌린 이벤트면 무엇이든 스킵"으로 처리하므로 키보드의 아무 키와 같은 결과가 나옵니다. 진입 직후 0.4초 스킵 유예도 그대로 적용됩니다.
- **모달**: HUD의 `_ready` 이후 HUD에 추가되는 Control(튜토리얼 모달 등)은 모달로 간주합니다. 모달이 떠 있는 동안에는 버튼을 숨기고 입력을 받지 않으며, 모달이 트리에서 빠지면 다시 표시합니다.

### 4.5 화면 비율: `aspect="keep"` 선택

Godot 4.6.1에서 `display/window/stretch/aspect`의 기본값은 이미 `keep`입니다(`ProjectSettings.get_setting`과 `property_get_revert` 양쪽으로 확인했습니다). 그래서 `project.godot`에 별도 설정을 추가하지 않았습니다. 에디터는 기본값과 같은 줄을 저장할 때 지우기 때문에, 적어 두어도 의미가 없습니다. `keep` 모드는 16:9가 아닌 화면에서 1280×720 캔버스 전체를 비율을 유지한 채 가능한 한 크게 그리고, 남는 영역을 검은 여백(레터박스)으로 채웁니다. 844×390 창에서 측정한 루트 변환은 배율 0.5414, 좌측 오프셋 76px였고, 실제 콘텐츠 영역은 693×390이었습니다. 이 배율에서 터치 버튼은 약 61px(DRIFT 약 71px, 일시정지 약 43px) 크기로 보입니다.

`expand`를 택하지 않은 이유는 다음과 같습니다.

- 표현 계층은 1280×720 좌표를 전제로 배치되어 있습니다. 손 앵커 (175, 276)/(1105, 276), 얼굴 눈 중점 (640, 248), Mode 7 셰이더 수평선 위치가 모두 그 좌표에 맞춰져 있습니다. `expand`로 가로를 넓히면 좌우에 설계되지 않은 영역이 드러나고, 배경 아트와 원단 뷰를 새 폭에 맞게 다시 조정해야 합니다.
- HUD는 앵커로 배치되어 있어 `expand`에서도 깨지지는 않지만, 위젯이 화면 가장자리로 벌어지면서 중앙 연출과 떨어집니다.
- `keep`은 기존 화면을 하나도 바꾸지 않습니다. 대신 20:9 폰에서는 가로 폭의 약 18%(좌우 76px씩)를 여백으로 버립니다. 이 여백을 활용하는 작업은 2단계 이후 과제로 남깁니다(§5.2).

`display/window/handheld/orientation`은 기본값이 이미 Landscape(0)라서 따로 적지 않았습니다. 에디터가 기본값 항목을 저장할 때 지우기 때문에 적어도 의미가 없습니다. 이 설정은 네이티브 export에만 적용되며, 웹 브라우저의 화면 방향은 고정하지 못합니다.

### 4.6 웹 export 설정

- `html/canvas_resize_policy=2`(Adaptive)는 이미 설정되어 있어 그대로 둡니다. 캔버스가 브라우저 창 전체를 채우고, 레터박스는 엔진이 캔버스 안에서 그립니다.
- `html/head_include` 끝에 `<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no, viewport-fit=cover">`를 추가했습니다. 기본 셸의 뷰포트 메타에는 `viewport-fit=cover`가 없어서, 노치가 있는 iPhone 가로 화면에서 Safari가 안전 영역 바깥을 페이지 배경으로 비워 둡니다. 같은 이름의 메타가 두 개 있으면 브라우저는 뒤에 나온 값을 적용하는데, `head_include`는 기본 메타보다 뒤에 삽입됩니다. 노치와 홈 인디케이터 영역은 `keep`의 좌우 레터박스 안에 들어가므로 게임 화면을 가리지 않습니다. 기존 OG/Twitter 메타는 그대로 보존했습니다.

## 5. 2단계 이후 계획

### 5.1 메뉴와 결과 화면 터치 레이아웃 (2단계)

- §2.5 표의 요소를 터치 모드에서 키웁니다. 버튼 최소 높이는 폰 환산 44px 이상(기준 좌표 약 82px)을 목표로 합니다.
- 설정 화면 슬라이더의 grabber와 트랙 높이를 키웁니다.
- 트랙 선택 캐러셀에 좌우 스와이프를 추가합니다.
- 리더보드 목록을 손가락 드래그로 스크롤할 수 있는지 확인하고, 안 되면 `ScrollContainer` 설정을 조정합니다.
- 가상 키보드: `html/experimental_virtual_keyboard`를 켜고 닉네임과 트랙 이름 입력을 실기에서 검증합니다. 문제가 있으면 JS `prompt()`로 입력받는 대체 경로를 둡니다.
- 인게임 HUD 캡션(RISK, FASTER/SLOWER, TIME)의 글자 크기를 터치 모드에서 키웁니다.

### 5.2 화면 비율 확장 (2단계)

- `expand` 모드로 전환하고, 표현 계층(배경, 얼굴, 손, 원단 뷰)이 넓어진 가로 폭을 채우도록 조정합니다. 이 작업은 `presentation.md`의 좌표 결정에 영향을 주므로 별도 설계가 필요합니다.
- 넓어진 좌우 영역에 터치 버튼을 옮기면, 버튼이 게임 화면(손과 원단)을 가리지 않고 엄지 위치에도 더 가까워집니다.
- 세로 화면 대응: 세로로 들고 있으면 `keep`에서 콘텐츠가 390×219 정도로 작아집니다. 세로 방향을 감지하면 "가로로 돌려 주세요" 안내를 띄웁니다.
- 터치 버튼 위치와 크기를 사용자가 조절하는 설정(왼손잡이 좌우 반전 포함)을 검토합니다.

### 5.3 트랙 에디터 터치 드로잉 (3단계)

- `DrawCanvas`에 `InputEventScreenTouch`/`ScreenDrag` 처리를 추가합니다. 한 손가락은 그리기, 두 손가락은 이동과 확대/축소(핀치)로 나눕니다.
- 키보드 단축키(Ctrl+Z, C, Backspace, Delete, Enter, Esc)에 대응하는 툴바 버튼이 모두 있는지 점검하고, 없는 기능은 버튼을 추가합니다.
- 트랙 불러오기/내보내기를 iOS와 Android 실기에서 검증합니다.

### 5.4 PWA, 전체 화면, 가로 고정 (3단계)

- `progressive_web_app/enabled`를 켜면 홈 화면에 추가한 앱이 브라우저 UI 없이 전체 화면으로 실행됩니다. 프리셋에는 이미 `progressive_web_app/orientation` 항목이 있으므로 가로 고정을 지정할 수 있습니다. 서비스 워커 캐시와 Cloudflare 캐시 Purge 절차(`deploy.md`)가 충돌하지 않는지 먼저 확인해야 합니다. 현재 `ensure_cross_origin_isolation_headers=true` 설정도 함께 검토합니다.
- 브라우저 안에서 전체 화면 버튼을 제공합니다. Android Chrome은 Fullscreen API와 `screen.orientation.lock("landscape")`(전체 화면 상태에서만 동작)을 지원합니다. iPhone Safari는 캔버스 요소의 전체 화면을 지원하지 않으므로 PWA 설치 안내가 현실적인 대안입니다.
- 주소창이 나타나고 사라질 때 캔버스 크기가 바뀌는 현상은 Adaptive 정책이 처리하지만, 실기에서 레이아웃이 튀지 않는지 확인합니다.

### 5.5 성능 프로파일 (3단계)

- 중급 Android 기기와 iPhone에서 FPS를 측정합니다. 측정할 때는 `Engine.get_frames_per_second()`를 화면에 표시하는 디버그 인자를 둡니다.
- 부하가 크면 다음 순서로 줄입니다. 먼저 `FabricSource`의 MSAA를 끄고, 다음으로 SubViewport 크기를 줄이며(512에서 384로), 그래도 부족하면 원단 셰이더의 연산량을 줄입니다.
- 첫 로딩 크기를 줄이기 위해 pck 안의 큰 텍스처(얼굴, 손, 배경)를 모바일용 해상도로 줄이는 방안을 검토합니다.

### 5.6 네이티브 export 선택지 (보류)

네이티브 앱은 계획에 없지만, 필요해지면 다음 순서로 진행할 수 있습니다.

- **Android**: Android export 템플릿, JDK, Android SDK, 디버그/릴리스 keystore를 준비하고 Android 프리셋을 추가합니다. 렌더러는 이미 모바일에서도 GL Compatibility로 지정되어 있습니다. 화면 방향은 기본값 Landscape가 적용됩니다.
- **iOS**: macOS와 Xcode, Apple Developer 계정(유료)이 필요합니다. App Store 심사 기준과 외부 리더보드 서버 통신(ATS, HTTPS)을 확인해야 합니다.
- 공통으로 1단계의 `TouchControls`는 `DisplayServer.is_touchscreen_available()`이 네이티브 모바일에서 true를 반환하므로 그대로 동작합니다. 리더보드 클라이언트는 웹이 아닌 릴리스 빌드에서 기본 서버 주소(`https://overlock.bnbong.com`)를 사용합니다. 네이티브 빌드는 웹보다 성능과 오디오 제약이 적은 대신 스토어 배포 부담이 추가됩니다.

## 6. 검증 방법

### 6.1 데스크톱 사전 검증

- 정적 검사: `gdparse`, `gdlint game`, `gdformat --check`를 통과해야 합니다.
- 실행 전 격리: 프로젝트를 스크래치 폴더에 복사하고, 사본 `project.godot`의 `[application]`에 `config/use_custom_user_dir=true`와 `config/custom_user_dir_name="<스크래치 절대경로>"`를 추가합니다. 사본도 프로젝트 이름이 같아서, 격리하지 않으면 실제 기록 파일(`user://`)을 덮어쓸 수 있습니다. `--headless --import`를 한 번 실행한 뒤 테스트합니다.
- 터치 버튼 강제 표시: `Godot --path . -- --touch-controls`로 실행하면 데스크톱에서도 버튼이 보이고, 마우스 왼쪽 버튼으로 버튼을 누를 수 있습니다.
- 폰 해상도 확인: `--resolution 844x390`, `--resolution 1280x720`처럼 창 크기를 바꿔 레터박스와 버튼 크기를 확인합니다.
- 멀티터치 확인: 테스트 스크립트에서 `InputEventScreenTouch`/`InputEventScreenDrag`를 index별로 만들어 `Input.parse_input_event()`로 보냅니다. 창 좌표로 보내야 하므로 `get_tree().root.get_final_transform()`으로 캔버스 좌표를 변환합니다. 헤드리스 모드에서는 창 크기가 0이라 이 변환이 무의미해지므로 `Viewport.push_input(event, true)`로 로컬 좌표를 보냅니다. 이때는 마우스 에뮬레이션이 일어나지 않으므로 필요한 경우 직접 흉내 냅니다.
- 마우스로 터치 흉내: 프로젝트 설정 `input_devices/pointing/emulate_touch_from_mouse`를 사본에서만 켜면 마우스가 터치 한 개로 변환됩니다. 이 설정을 켜면 `is_touchscreen_available()`도 true가 되므로 원본 프로젝트에는 켜지 않습니다.
- 브라우저 에뮬레이션: 웹 빌드를 `tools/web_serve.py`로 띄우고, Chrome DevTools의 기기 툴바(iPhone 프리셋, 가로 방향)에서 터치 이벤트와 뷰포트를 확인합니다. 실제 멀티터치와 오디오 정책은 에뮬레이션으로 확인할 수 없습니다.

## 7. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| iOS에서 AudioContext가 첫 탭 이후에도 풀리지 않을 수 있습니다. | 무음으로 플레이하게 됩니다. | 엔진이 `touchend`에서 resume을 호출하는 것을 소스로 확인했습니다. 실기에서 문제가 재현되면 `head_include`에 `touchend` 리스너로 resume을 한 번 더 호출하는 스크립트를 추가합니다. |
| iOS 무음 스위치가 켜져 있으면 Web Audio가 소리를 내지 않습니다. | 사용자가 버그로 오인할 수 있습니다. | 웹 페이지에서 제어할 수 없는 동작이므로 안내 문구로 대응합니다. |
| 앱 전환이나 알림으로 `touchend`가 오지 않으면 버튼이 눌린 채 남을 수 있습니다. | 조향이 한쪽으로 고정됩니다. | 웹 템플릿은 `touchcancel`을 `touchend`와 같은 뗌으로 처리합니다. 추가로 `TouchControls`가 창이나 앱 포커스를 잃을 때 눌린 액션을 모두 뗍니다. 실기 체크리스트 16번으로 확인합니다. |
| 폰 화면에서 HUD 글자와 메뉴 버튼이 너무 작습니다. | 가독성과 조작성이 떨어집니다. | 2단계(§5.1)에서 해결합니다. |
| 가상 키보드가 뜨지 않습니다. | 닉네임과 트랙 이름을 수정할 수 없습니다. | 최초 닉네임은 미리 채워져 있어 진행은 막히지 않습니다. 2단계에서 가상 키보드를 검증합니다. |
| 모바일 GPU에서 원근 셰이더와 SubViewport 부하로 FPS가 떨어질 수 있습니다. | 조작감이 나빠집니다. 판정은 고정 스텝이라 영향이 없습니다. | 3단계(§5.5)에서 프로파일링합니다. |
| 약 44MB(wasm과 pck 합계, 8월 빌드 기준이며 최근 스크래치 빌드는 `index.pck`만 약 26MB로 더 큽니다)의 첫 다운로드가 느립니다. | 모바일 데이터 환경에서 이탈할 수 있습니다. | 3단계에서 텍스처 축소와 PWA 캐시를 검토합니다. |
| 터치 버튼이 손과 원단 일부를 가립니다. | 시야가 일부 줄어듭니다. | 버튼을 반투명으로 두었습니다. 2단계에서 `expand` 여백으로 옮기는 방안을 검토합니다(§5.2). |
| 튜토리얼과 터치 버튼의 터치 판별 기준이 일부 환경에서 다를 수 있습니다. | 안내 문구와 실제 조작 수단이 어긋납니다. | §4.3에 적은 대로 필요하면 `TouchControls.should_show()`로 통일합니다. |
