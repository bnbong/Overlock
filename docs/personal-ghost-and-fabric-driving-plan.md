# 개인 최고 기록 고스트와 원단별 주행 특성 계획

작성일: 2026-10-01. 현재 루트 소스 확인을 바탕으로 한 구현 계획이다. 계수는 밸런스 검증 전 초기 제안이며 제품 코드는 변경하지 않았다.

두 기능의 공통 전제는 같은 트랙과 같은 주행 규칙의 기록끼리 비교하는 것이다. 먼저 기록 호환성 기준을 만들고 개인 고스트를 추가한 뒤 원단별 물리를 적용한다.

## 현재 구조와 설계 결정

- RecordStore는 records.json에 track_id|difficulty 키로 결과를 저장하며 final_time_ms가 더 작은 경우 신기록으로 판정한다.
- RunStats의 final_time_ms는 순수 주행 시간 finish_ms와 penalty_ms의 합이다. 온라인 리더보드는 등급 우선이므로 로컬 개인 최고와 동일하지 않다.
- RaceDirector._finish에서 기록이 확정된다. 에디터 테스트는 이미 GameState.is_editor_test로 기록 저장을 제외하므로 이 경로를 유지한다.
- MiniMap은 전체 트랙이 아니라 현재 위치 주변의 회전된 경로 일부를 그린다. 멀리 떨어진 고스트가 화면 밖에 있는 것은 정상이다.
- PlayerController는 속도 단계, 조향 지연, 회전력, RISK 누적을 Tuning에서 읽는다. fabric은 현재 주로 원단 렌더링과 메타데이터에 쓰인다.
- 공식 트랙 체크섬과 로컬 경로 체크섬, 허브 content_hash의 의미가 다르다. 기존 제출용 체크섬을 다른 계산으로 바꾸지 않는다.
- 서버에 game_version은 저장되지만 순위 조회는 현재 트랙·난이도 기준이다. 버전 문자열을 올리는 것만으로 물리 규칙이 다른 기록을 분리할 수 없다.

## 1 개인 최고 기록 고스트

### 사용자 경험

트랙 선택 화면에 “개인 고스트 켜기/끄기”를 제공하고 설정을 저장한다. 기본은 켜기이며 호환되는 기록이 없으면 “첫 완주 후 고스트가 생깁니다” 또는 “이전 기록에는 고스트가 없습니다”라고 표시한다.

첫 버전은 미니맵의 반투명 마커와 구간 기록 차이로 구성한다. 중앙 원단에 두 번째 손·얼굴·노루발을 그리지 않는다. 마커 모양과 라벨로 플레이어/고스트를 구분하고 색상만으로 구분하지 않는다.
고스트가 부분 미니맵 밖에 있으면 경계 방향 표시를 사용하거나 마커를 숨기고 시간차만 유지한다. 현재 플레이어와 같은 좌표 변환을 사용한다.

트랙을 호길이 기준 10개 구간으로 나눠 통과 시 “개인 최고보다 0.42초 빠름/느림”을 잠시 표시한다. 최종 구간은 실제 완주 지점을 쓴다. 패널티 포함 비교임을 UI에 설명하며 부상 대사·아이템·터치 버튼과 겹치지 않는 HUD 위치를 사용한다.

### 고스트 선택과 시간 기준

- 현재 로컬 정책을 유지해 패널티 포함 최종 시간이 가장 빠른 완주의 고스트를 보관한다. 등급 우선 고스트를 별도로 추가하지 않는다.
- 동률이면 기존 기록을 유지한다. 로컬 최고와 온라인 순위 기준이 다름을 트랙 선택/결과에서 간단히 설명한다.
- 미니맵 고스트의 위치는 카운트다운 후 실제 주행 경과 시간으로 재생한다. 패널티가 생겨도 화면상의 시간을 강제로 앞으로 당기지 않는다.
- 구간 기록 차이는 현재 구간의 (주행 시간 + 그때까지 누적 패널티)에서 고스트의 같은 구간 값을 뺀다. 음수는 빠름, 양수는 느림이다.
- 두 기준은 다르므로 고스트 마커가 앞에 있는데 패널티 포함 기록은 느릴 수 있다. 안내 문구에 명시한다.
- 일시정지·튜토리얼·카운트다운·결과 줌아웃은 기록/재생 시간에서 제외한다. 고스트는 자체 완주 후 도착 표시를 잠시 남기고 정지한다.

### 기록 방식

입력 재시뮬레이션 대신 위치 스냅샷을 저장한다. 서버 검증용 리플레이나 치트 판정으로 쓰지 않는다.
물리 틱에서 20Hz 간격으로 t_ms, 월드 x/y, heading, 진행 s를 기록하고 렌더에서는 인접 샘플을 보간한다. 각도는 각도 보간을 사용한다. 물리 주기가 바뀌어도 실제 시각을 저장하며 렌더 FPS에 샘플링을 묶지 않는다.

출발·완주 및 강제 복귀는 별도 이벤트 샘플을 남긴다. 복귀 전후를 직선 보간하면 트랙을 가로질러 날아가므로 discontinuity 플래그로 즉시 이동한다. 고스트는 충돌·아이템 획득·RISK·기록에 영향을 주지 않는다.

구간 통과는 물리 틱에서 계산한다. 최대 진행도와 최초 통과를 이용해 후진/같은 구간 재방문 중복을 막는다. 이전/현재 진행도 사이에서 선형 보간하되 복귀 이벤트로 건너뛴 구간은 가상 통과 시간을 만들지 않고 비교 불가 처리한다. 결승은 RaceDirector의 실제 완료 판정에 맞춘다.

샘플 최대 24000개, 파일 최대 2MiB를 초기 상한으로 둔다. 20Hz 기준 약 20분이며 이벤트 샘플은 같은 상한에 포함한다. 한도에 닿으면 해당 런의 고스트 저장을 중단하고 기록 저장은 계속한다. 결과에 고스트 미생성 이유를 표시하며 뒤가 잘린 고스트를 정상 파일로 게시하지 않는다.
초기 포맷은 compact JSON의 숫자 배열로 충분하다. 이 단계에서 바이너리 코덱·압축 프레임워크를 추가하지 않는다.

### 저장과 호환성

고스트 헤더: format_version, run_id, track_id, difficulty, track_fingerprint, physics_ruleset, finish_ms, penalty_ms, final_time_ms, sample_count.
내용: 위치 샘플과 10개 구간의 통과 시간/누적 패널티/유효 여부.

track_fingerprint는 정규화한 플레이 데이터 전체(경로·닫힘·폭·재질·아이템·실제 소비 modifiers)를 대상으로 한다. 표시명·작성자·설명·로컬 저장 ID는 제외한다. 허브의 정규화/해시 도구를 먼저 검토해 재사용하되 필요한 필드가 빠져 있으면 별도 로컬 fingerprint를 둔다.
physics_ruleset은 게임 릴리즈 버전과 구분한다. HUD/문구 수정으로 고스트를 무효화하지 않고 실제 물리·판정·아이템 규칙 변경 시에만 갱신한다.
허용된 조향 감도는 사용자의 선택이므로 동일 규칙 내에서 비교 가능하게 유지하고 참고 메타데이터로 기록한다. 개발용 tuning override는 별도 practice 규칙으로 분리하거나 정확한 설정 해시를 사용해 정식 기록과 섞지 않는다.

저장 순서:
1. 새 고스트를 고유 run_id 임시 파일에 쓰고 구조·크기·시각 단조성을 검사한다.
2. 임시 파일을 최종 파일로 교체한 뒤 기록 엔트리에 해당 run_id/파일을 연결해 저장한다.
3. records.json도 임시 파일→교체 방식으로 저장한다. 실패하면 이전 메모리와 기존 기록을 보존한다.
4. 새 기록과 참조가 저장된 뒤에만 이전 고스트를 정리한다. 중간 종료의 고아 파일은 다음 실행 때 정리할 수 있다.

고스트 쓰기가 실패해도 최고 기록 저장은 시도한다. 이 경우 새 최고에는 고스트 없음으로 표시하고 이전 고스트를 새 최고인 것처럼 보여주지 않는다. 최고 기록 저장 자체가 실패하면 기존 최고와 고스트를 유지한다.
파일 손상·지원하지 않는 포맷·fingerprint/ruleset 불일치면 고스트만 비활성화한다. 기존 기록을 삭제하거나 게임 진입을 막지 않는다.
커스텀 트랙 삭제와 RecordStore.purge에서 해당 기록의 고스트를 함께 정리한다. user:// 웹 저장은 현재 영속 방식에 맞춰 재실행과 IDBFS 동기화 실패까지 검사한다.

기존 records.json은 백업 후 새 버전 포맷으로 읽기 호환 마이그레이션한다. fingerprint/ruleset이 없는 기록은 “이전 버전 기록”으로 보존하며 현재 규칙의 최고로 자동 간주하지 않는다. 새 호환 기록이 더 느려도 새 규칙의 첫 최고/고스트가 될 수 있어야 한다.

## 2 원단별 주행 특성

### 기본 경험과 범위

첫 버전은 트랙 전체에 한 가지 원단 특성을 적용한다. 원단마다 조작 결과가 일정해야 하며 무작위 미끄러짐이나 무작위 부상을 추가하지 않는다.
트랙 선택·에디터·허브 상세에서 원단 견본 옆에 “표준 / 느리지만 안정적 / 반응이 늦고 위험도 상승”처럼 플레이 차이를 표시한다.
부상 슬립 연출과 원단의 조향 지연은 별개다. 실크라는 이유로 손가락 부상을 직접 발동하지 않고 기존 RISK 계산을 거친다.

### 첫 밸런스 표

모두 기본 튜닝에 대한 배율이다. 실제 주행으로 조정할 시작값이며 확정 스펙이 아니다.

| 원단 | 속도 | 조향 지연 시간 | 위험 누적 속도 | 성격 |
|---|---:|---:|---:|---|
| 면 cotton | 1.00 | 1.00 | 1.00 | 현재 기준 조작감 |
| 데님 denim | 0.94 | 0.90 | 0.85 | 조금 느리지만 안정적 |
| 실크 silk | 1.04 | 1.15 | 1.10 | 빠르지만 반전 조향에 주의 |
| 니트 knit | 0.98 | 1.08 | 0.95 | 부드럽고 약간 늦는 반응 |
| 울 wool | 0.95 | 1.00 | 0.90 | 느리고 위험 누적이 낮음 |
| 펠트 felt | 0.96 | 0.88 | 0.90 | 낮은 속도와 빠른 반응 |
| 새틴 satin | 1.02 | 1.10 | 1.05 | 실크보다 완만한 변화 |
| 가죽 leather | 0.92 | 0.95 | 0.85 | 낮은 속도로 안정적인 재봉 |

먼저 면·데님·실크 세 종류로 계수 적용 및 체감을 확인하고 나머지 다섯 종류를 같은 구조로 적용한다. 최종 범위는 8종 지원이다. 8종마다 새로운 물리 공식을 만들지 않는다.
길이·판정 폭·등급·패널티 초·아이템 지속 시간·부상 사전 연출 시간은 이번 원단 계수로 바꾸지 않는다.

### 물리 연결

작은 FabricProfile 데이터 테이블을 만들고 런 시작 시 TrackData.fabric으로 결정해 PlayerController에 고정 전달한다. 전역 Tuning 값을 수정해 다음 트랙으로 계수가 누적되는 방식은 피한다.

- effective_speed_table = 기본 speed_table × 속도 배율.
- effective_steer_tau = 기본 steer_tau × 지연 배율.
- effective_risk_gain_rate = 기본 risk_gain_rate × 위험 배율.
- risk 계산의 속도 비율과 회전력 계산의 max_speed는 동일한 effective 최소/최대 속도를 사용한다. 속도 배율을 분모에만 빠뜨려 의도하지 않은 위험/회전 변경을 만들지 않는다.
- 위험 배율은 기존 danger_threshold 판정 이후 누적률에만 적용한다. 회복률·골무 0.95 상한은 유지한다. 지연 증가 자체도 위험 계산에 영향을 주므로 실크에서 효과가 이중으로 커지는지 측정한다.
- reset_state, 기어 변경, cut 감속, off-fabric 복귀의 모든 speed 대입에 effective table을 사용한다. 일부 경로만 기본값으로 되돌아가지 않게 공통 함수를 사용한다.
- 엄마 찬스의 자동 진행 거리 계산도 동일한 실제 속도를 사용한다. 골무의 부상 면역과 엄마 찬스의 온레일 보호는 유지한다. 현재 수동 아이템 사용/보관 슬롯 동작을 보존한다.
- unknown/빈 원단의 로컬 재생은 면 기준으로 fallback하며 사용자에게 기본 특성임을 안내한다. 허브 업로드는 기존 허용 목록 검증을 유지한다.
- 혼합 원단 문자열은 구간 정보를 의미한다고 추정하지 않는다. 첫 버전은 물리 표준 프로필 fallback으로 명시하고, 구간별 원단 전환은 별도 데이터 설계 후 진행한다.

최저 속도에서도 기존 유효 트랙을 완주할 수 있어야 한다. 실크의 속도 상승은 최소 회전반경을 키울 수 있으므로 TrackValidator 하드 최소반경 28 부근 트랙을 검사한다. 불가능한 트랙이 생기면 규칙을 몰래 완화하지 말고 속도 배율을 줄이거나 저속 기어만 배율을 1로 유지하는 방안 중 최소 변경을 택해 문서화한다.

## 3 기록 공정성과 서버 호환성

물리 변경 공개 전에 서버도 ruleset 기준을 지원해야 한다. 클라이언트만 먼저 배포해 이전 기록과 섞지 않는다.

- Run에 physics_ruleset을 추가하고 기존 행/해당 필드 없는 구클라이언트 요청은 legacy로 분류한다. 새 클라이언트는 명시된 새 규칙을 보낸다.
- leaderboard 조회·플레이어별 최고·순위·count를 같은 ruleset으로 필터한다. 캐시와 제출 당시 순위 저장 키에도 반영한다.
- 구클라이언트 조회에 ruleset이 없으면 legacy를 반환해 기존 동작을 유지한다. 새 화면은 현재 규칙을 기본으로 하고 과거 기록은 별도 선택으로 보존한다.
- 서버는 허용 ruleset과 game_version 조합을 검증하고 알 수 없는 규칙은 거부한다. 이것이 물리 리플레이 검증을 대신한다고 주장하지 않는다.
- 신규 컬럼·인덱스는 명시적 데이터 마이그레이션을 작성한다. create_all만으로 기존 테이블이 바뀐다고 가정하지 않는다. 백업·롤백 절차를 포함한다.
- 물리 최소 시간 필터는 트랙의 원단과 ruleset별 실제 최대 속도로 계산한다. 기존 Track.min_final_time_ms 하나를 덮어써 legacy 판정까지 바꾸지 않는다.
- 공식 트랙 바이트 체크섬과 서버/클라이언트 트랙 동기화는 유지한다. 원단 프로필 변경은 ruleset이 담당한다.
- 커뮤니티 트랙은 계속 로컬 기록 전용이다. 이번에 커뮤니티 리더보드를 추가하지 않는다.
- 공유 허브 트랙 JSON은 fabric ID를 유지한다. 게시자는 원단을 선택할 수 있지만 임의의 물리 계수를 업로드할 수 없다.

## 4 파일별 구현 방향

| 위치 | 변경 |
|---|---|
| RecordStore.gd | 호환 기록 키·마이그레이션·최고/고스트 연결·안전한 저장 |
| 작은 GhostRun/GhostStore 모듈 | 샘플 기록/보간·파일 검증, 기존 저장 코드와 책임 중복 방지 |
| RaceDirector.gd | 주행 시작·물리 샘플·구간·복귀 이벤트·완주 확정 연결 |
| MiniMap.gd / HUD.gd | 고스트 마커·구간 시간차 |
| TrackSelectScreen.gd / SettingsScreen.gd | 고스트 토글·호환 상태·원단 특성 안내 |
| ResultScreen.gd | 새 고스트 저장 성공/실패, 이전 규칙 기록 구분 |

| TrackData / TrackLoader 및 에디터·허브 표시 | 전체 내용 fingerprint와 원단 설명 |
| 서버 모델·스키마·조회·제출·시간 하한·마이그레이션 | ruleset 분리와 구버전 호환 |

기존 에디터 개선·아이템 슬롯·공유 허브 작업이 진행됐으므로 구현 시작 시 최신 루트 및 작업 브랜치를 다시 확인한다. 예전 코드 스냅샷을 덮어쓰지 않는다.

## 5 단계와 검증

1. 기록의 fingerprint/ruleset 계약, 이전 기록 보존, 안전한 저장을 먼저 구현한다.
2. 현재 물리 그대로 고스트 기록/재생과 10구간 비교를 구현한다.
3. 원단 테이블과 면·데님·실크를 로컬에서 검증한다. 이후 8종을 완성한다.
4. 서버 ruleset 분리·구버전 API 호환·시간 하한 검증을 완료한다.
5. 고스트와 새 원단 물리를 함께 검증한 뒤 서버 선배포→클라이언트 적용 순서로 공개 준비한다. 실제 운영 배포는 별도 작업이다.

필수 검사:
- 고스트 ON/OFF에서 동일 입력의 주행 위치·시간·RISK·아이템·최종 결과가 동일.
- 30/60/120 렌더 FPS에서 동일 물리 시간의 고스트 위치 일치, 보간 및 복귀 순간 이동 처리.
- 순수 주행은 빠르지만 패널티 포함 느린 런, 동일 시간, 고스트가 먼저 완주한 경우, 구간 후진/복귀/건너뜀.
- 최고 미갱신·갱신·고스트 파일 실패·기록 저장 실패·중간 종료·손상 파일·용량 초과·웹 재실행.
- 테스트 플레이·중도 포기·재시작은 최고/고스트를 덮어쓰지 않음.
- 같은 custom ID의 경로/원단/폭/아이템 수정 시 옛 고스트를 사용하지 않음. 표시 이름만 바꾸면 비교 가능.
- 면 profile은 동일 입력에서 기존 물리와 같은 결과. 각 원단의 전 기어·좌우 유지/반전·드리프트·골무·엄마 찬스·부상/강제 복귀·최소반경 트랙을 확인.
- 실크에서 1~2단의 기본 안전성, 고속의 위험 증가, 데님의 낮은 위험 누적을 측정. 단순 배율만 보고 체감이 확정됐다고 하지 않음.
- 이전/현재 ruleset의 순위·count·플레이어 최고·제출 rank가 섞이지 않음. DB 기존 기록 보존 및 롤백 검증.
- 모바일에서 구간 시간차가 미니맵·부상 대사·RISK·터치 조작을 가리지 않음.

고스트는 로컬 기능이며 서버 업로드·공유·전체 입력 리플레이·화려한 유령 캐릭터는 이번 범위가 아니다. 원단별 구간 전환과 랜덤 기믹도 후속 범위다. 최종 밸런스와 출시 버전 번호는 구현·플레이 검증 후 결정한다.
